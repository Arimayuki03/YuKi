## T4 — Kazumi 历史卡点击报「缺少站点或视频 id」

**根因（两层）**

1. 历史卡点击处理器**没有 kazumi 分支**。`records.js:279-296` 只有两条路：`site === 'bangumi'` → `Kazumi.openBangumiInfoPage(id)`；其余全部 → `Detail.open(site, id, name)`。对比搜索页 `search.js:53-89` **有** `src.startsWith('kazumi:')` 分支走 `Kazumi.openSourceDialog`。
2. Kazumi 播放记录的 `vodId` 是空的。`player.js:317-326` 从 `Detail.vodId` 取 `vodId`——从 Kazumi 弹窗直接起播时该值为空；若之前开过 CatVod 详情页，则会**串入别的源的 id**。

于是命中 `detail.js:126-127` 的守卫：`if (!site || !vodId) { warnToast('缺少站点或视频 ID'); return; }`

**次生失败形态**：`vodId` 非空（串入的 id）时守卫放行，`detailContent` 带 `site='kazumi:baimao'` 打到后端，`server.py:167` 抛 `no site loaded` → 404（`server.py:319`）→ 前端显示「未取得详情」。所以用户可能看到两种错误之一。

**实证**（来自线上 `settings.json` 的 `recentWatches`，同一写入器）：
- `{site:"kazumi:7sefun", vodId:"", name:"尼古喵喵"}` → 空 id
- `{site:"kazumi:baimao", vodId:"145024", ...}` 与 `{site:"量子资源", vodId:145024, ...}` 并存 → `145024` 属于量子资源，不属于 baimao

**字段名并无差异**：CatVod 与 Kazumi 记录都是 `{site, siteName, vodId, name, pic, remarks, ts, kind, ...}`（`records.js:64-80`）。差的是**语义与完整性**：

| | CatVod 记录 | Kazumi 记录 |
|---|---|---|
| `site` | 源 key，如 `量子资源` | `kazumi:<pluginName>` |
| `vodId` | 真实 CMS vod id | `''` 或串入的 CatVod id |
| 剧集源页 URL | 不需要 | **必需但从未存储** |

Kazumi 详情的正常入口需要 `pluginName` + 番剧**源页 URL**：`kazumi.js:941-952`（`openSourceDialog` → `_loadChapters`）、`kazumi.js:1553-1556`（`kazumiChapters` 带 `{pluginName, src}`）。搜索页把 `src` 放在 `data-id`（`search.js:456`）。

**修复方向**
- `records.js:279-296` 增加 `kazumi:` 分支，镜像 `search.js:57-87`，调 `Kazumi.openSourceDialog(name, site, srcUrl)`。
- 把番剧源 URL 从 `kazumi.js:1166/1553` 一路穿到 `Player.play` → `_curMeta`（`player.js:326`）→ 记录字段（`records.js:68-74`），例如新增 `kazumiSrc`。
- 堵住 `Detail.vodId` 泄漏：`player.js:318-321` 对非 CatVod site 不再取 `Detail.vodId`。
- `detail.js:146-176` `openBangumi` 补 `this._vod = null`。

**顺带发现的两个缺陷（同批修）**
- **跨引擎按片名合并**：`records.js:32-52` 用 `site: v.site || old.site`、`vodId: v.vodId || old.vodId`，同名影片在 CatVod 与 Kazumi 之间会互相改写来源。
- **`openBangumi` 不清 `_vod`**：导致 `toggleFav`（`detail.js:574-583`）写出 `site: ''` 的收藏。线上确有此数据：`{site:"", vodId:"322898", name:"在地下城…第三季", bangumiId:"291412"}`。点这种收藏卡同样触发 `detail.js:127` 的守卫。

**验收**

1. **每条要多一次 `/v0/me` 往返**。`bangumi_update_collection` 在 `plugin_manager.py:863-864` 每次调用都清用户名缓存，并最多暴力尝试 8 种组合（2 base × 2 username × POST/PUT，`:877-884`）。50 条的批量上传会很慢——**应在批次内缓存 username**。

3. **远端收藏读取硬上限 100 且无分页**（`plugin_manager.py:816` clamp 100，而 `server.py:812` clamp 200，实际生效 100）。收藏超过 100 部的用户会拿到**被截断**的远端集合，直接影响「是否已存在」判断的正确性。
